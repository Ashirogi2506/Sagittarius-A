# Player controls prototype

These scripts are a starting point for the team's Unity project, not a completed scene or a replacement for another member's gameplay system. No existing scene, prefab, input settings, UI, or models are changed. They use `UnityEngine.Input` (legacy Input Manager with `Mouse X` / `Mouse Y`): the real project must enable the legacy input API or the team must adapt the input calls to its chosen system. The exact Unity version and input system are not yet known; this code has not been verified in Unity.

1. Add a `CharacterController`, `PlayerInventory`, and `PlayerController` to the player, and assign the child camera to `viewCamera`. Configure the controller capsule, collision and movement speed to suit the scene.
2. Expand **Controls** on `PlayerController` in the Inspector. Forward/back/left/right and interact, pickup, inventory, use and break/open each have editable keys. W/A/S/D, E, F, Tab, Q and R are provisional starter settings, not confirmed final bindings. Mouse look sensitivity, gravity and interaction distance are adjustable there too. The project input settings need the standard `Mouse X` and `Mouse Y` axes. Resolve key conflicts with the gameplay owner.
3. Add `PlayerWorldTarget` to a collider or its parent. Set the supported actions. Assign persistent Inspector callbacks to `onInteract`, `onPickup`, and/or `onBreakOpen`; these callbacks must actually change the object or open the relevant interaction. A pickup additionally needs a nonempty item ID; the inventory records it and prevents repeat pickup. Nothing automatically breaks, disappears, triggers a repair, or creates an item effect without those scene-owned callbacks. Give interactable objects colliders and put them on a layer included by the player.
4. The UI owner subscribes to `InventoryOpenRequested`, opens their inventory panel, then calls `NotifyInventoryOpened()` after the panel is open. Use `PlayerInventory.GetItem`, `Count`, and `Changed` to display items; call `SelectInventoryItem` when the user selects an item. The gameplay owner assigns `UseItem` to an item-effect handler which returns true only on success; the tutorial advances on successful use. The handler decides whether the item is consumed using `TryRemoveAt`.
5. Add `PlayerTutorialBridge` to a startup object, assign the player, and assign `FarSignal.ControlsTutorial.json` as `tutorialJson`. Wire `instructionChanged` to the tutorial UI text and `tutorialFinished` to the UI controller. The bridge starts its sequence in `Start()`. Ensure the starting area and tutorial UI support the selected steps. A scene owner must configure these references. If controls change at runtime, call `RefreshBindingLabels()`.

`PlayerController.ActionCompleted` emits `move`, `look`, `interact`, `pickup`, `inventory`, `use`, and `break` only on the implemented success conditions. Input polling, camera movement, cursor locking, pause/menu behavior, inventory persistence, pickup effect callbacks, item use effects, and playable level setup must be coordinated with the team's gameplay owner. Event callbacks are Inspector-wired; their effect must be implemented and verified in the scene. Duplicate or conflicting key assignments are not automatically resolved.
