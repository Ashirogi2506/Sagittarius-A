# Gameplay bridge examples

These examples were checked against `feature/gameplay-ui` at commit `696f80a548044dc5cbe715c715694227c9338b97`. They are `.cs.txt` intentionally: they are opt-in handoff examples, not a second compiled copy of gameplay code. A gameplay owner can review and place the approved implementation in the gameplay assembly, which already references MissionSimulation. They do not bind themselves to any scene, event, or player save.

`EarthCompletedSnapshotMapper` translates the completed team catalog, build and locked cargo into simulation data and runs the existing Earth validator. `EarthCheckpointBridge` also requires an explicit arrival-time confirmation, observed power state, run ID and commander identity before preparing a verified checkpoint. Neither reads or writes PlayerPrefs, starts the Moon, or spends fuel.

The team currently completes power and landing checks in flight; this checkpoint is a forward handoff snapshot after those checks, not proof that they occurred before launch. It is not an authorized replacement for a pre-launch recovery save. The team's DTO does not currently supply all of the requested facts: the caller must receive the real arrival confirmation and power/laser state from the activity rather than inventing them. The gameplay Moon controller already calls `LunarDescent`; use a single authoritative save/transaction owner so a landing never spends fuel twice. Decide save ownership and recovery behavior before wiring the bridge. Insufficient-fuel behavior remains a team-lead decision.

Local verification covered the valid basic loadout, locked cargo, unconfirmed arrival, missing and inconsistent observed power, commander Unicode, copied data, and checkpoint restore. The bridge also compiled and its basic handoff ran inside the isolated Unity project. No gameplay event, actual existing save migration, scene transition, or interactive playthrough was tested by these examples.
